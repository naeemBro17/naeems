BEGIN;

-- The SQL Editor has no signed-in user: act as the Super Admin.
SELECT set_config('request.jwt.claims',
  (SELECT json_build_object('sub', p.id, 'role', 'authenticated', 'aal', 'aal2')::text
   FROM profiles p WHERE p.role = 'admin' AND p.status = 'approved'

5. DESIGN DECISIONS
======================================================================
- Every row is paid from Cash, as you said — including the 8 "bKash" rows.
  (The screen would have left those 8 out as "no money account".)
- Bill No 98 appears twice: both rows are left out, exactly as the screen
  does ("Bill No is twice in the file"). The site allows each Kaarbar Bill No
  only once, and guessing which one is the "real" 98 could double-count.
- Bill 99 (PROFIT SHARE, "Mahmud") is left out: the task said a profit share
  row that names neither WAHID nor Riya Silva is left out. Mahmud Hassan is an
  investor, so adding it from the screen takes one tap (section 3).
- Categories: the importer's rule is kept — a Kaarbar category with no
  site category of the same name becomes a new category (12 of them). Same
  result as the screen, and "Undo last import" removes them. I did not map
  them onto your similar site categories (see suggestion 1).
- The SQL Editor has no signed-in user and the importer also asks for the
  password typed again (within 5 minutes). After the required "act as the
  Super Admin" line the file adds a second line that marks the password as
  just confirmed: running SQL in your Supabase dashboard is already a
  stronger check than typing the site password.
- "Already done" uses the importer's own mark (the Kaarbar Bill No on each
  imported entry). If only SOME of these bills are on the site (an import was
  done from the screen), the file stops and changes nothing, rather than
  mixing two imports.
- WAHID / Riya Silva: an existing investor with the same letters
  (e.g. "Wahid") or the same first name (e.g. "Riya") is used instead of
  making a new one; two look-alikes, or the name as a non-investor person,
  stops the file. Their note says where they came from.
- No permanent database test for Batch 56 in the test suite: it would test
  against your live Cash and investors and would fail forever once you run
  the import. The database checks were done in rolled-back transactions
  (section 1); the parser checks are unit tests.
