PART 5 — Real order steps from Steadfast
  Steps (customer page, My Orders and admin):
    Order Placed → Processing → Booked → In Transit → Out for Delivery →
    Delivered; side states Partly delivered, Cancelled / Returning, On
    hold, Needs attention. The exact rules:
      order pending → Order Placed; confirmed → Processing
      booked, Steadfast in_review or no status yet → Booked
      Steadfast pending → In Transit
      tracking text "sent to / received at / arrived at / returned to …
        hub / warehouse" → In Transit (any case, any hub name)
      tracking text "assigned to rider" / "rider assigned" / "out for
        delivery" → Out for Delivery
      "consignment created" → Booked
      any other text → nothing (the last known step stays; never guessed
        forward). The newest recognised text wins, with the status as the
        floor, so a failed attempt (back at the hub) shows In Transit.
      delivered → Delivered
      delivered_approval_pending → customer: Delivered; admin:
        "Delivered — awaiting Steadfast confirmation"; the stored order
        and the COD payment change only on confirmed "delivered"
      partial_delivered* → Partly delivered
      cancelled* (incl. every return status) → Cancelled / Returning
      hold → On hold
      exceptional / unknown / unknown_approval_pending → Needs attention
        (customer sees "Delayed — we're checking")
      order cancelled on the site → Cancelled
      marked shipped by hand without Steadfast → In Transit
  - New steadfast function action "tracking" (GET
    /trackings_by_invoice/{invoice}) + the current status. Called when an
    order page opens (customer or admin) and in the 3-hourly refresh. One
    Steadfast call per order per minute at most: the last answer is kept in
    a staff-only table and a 60-second phone cache.
  - Customer page: a clean vertical list (done = check, current
    highlighted, later grey), Steadfast's latest words and time under the
    current step. NO rider name or phone: any rider text becomes "Assigned
    to a rider — your parcel is out for delivery.", phone numbers are
    removed (done in the function AND again on the page). "Track parcel on
    Steadfast" stays.
  - Admin: the same steps plus the full Steadfast timeline (rider
    included). "Check delivery status" refreshes both.
  - If the new action isn't deployed, pages show what is saved on the
    order, with no error. Stored status values are unchanged; the admin
    filter "Shipped" is now "With courier".
  Proof: 25 unit tests of every rule above; Part 5 e2e (all four steps,
  no rider details, admin timeline, missing action = old display);
  screenshots customer-order-{booked,in-transit,out-for-delivery,
  delivered}-*, admin-order-timeline-*.

5. DESIGN DECISIONS
-------------------
  - Customers = grouped by phone (registered or not), because most of your
    customers come from Facebook / WhatsApp and never sign up.
  - "Partly paid" etc. are worked out from payments at read time; the old
    payment_status column is kept in step so the invoice, Telegram and the
    old site agree.
  - Add payment needs "Change order status" (it already covered "mark
    paid") — no extra switch. Edit / delete / refund: you only.
  - A booked order's COD is "what is due". When Steadfast confirms
    delivery, the amount recorded is the COD Steadfast was actually given
    (if you never updated it, Steadfast collected the old amount).
  - The "Open on Steadfast" button goes to
    https://steadfast.com.bd/user/consignment/<id>. The guide doesn't give
    the merchant page address, so please check it opens the parcel
    (section 8). One line to change in src/lib/orderEdit.ts if not.
  - Steps use near-black checks and grey; no orange. The Steadfast banner
    uses the existing soft warning colour.
  - E2e tests can never reach the real Steadfast: every test page gets a
    mocked Steadfast function by default (e2e/fixtures.ts).
