2. NEEDS FUTURE WORK (highest severity/impact first)
------------------------------------------------------

[MEDIUM — Performance] No code-splitting: every visitor downloads the entire admin panel
  What it means for the business: a first-time visitor from a Facebook ad has to download
  ~700KB of JavaScript (before compression; ~196KB after) before the page becomes
  interactive — and that includes all the code for CSV import, the admin image editors, the
  banner editor, etc., which a customer will never use. On a slow mobile connection in
  Bangladesh this directly costs you money on ads (slower page = more people leave before
  it loads = wasted ad spend).
  Status: Needs a future batch. Effort: Medium.
  Fix approach: split /admin into its own downloaded chunk using React's built-in lazy
  loading, so customers only download the customer-facing code, and the admin code only
  loads when Naeem himself opens /admin.

[MEDIUM — Performance] Product photos are sent at full size to small thumbnails
  What it means for the business: I measured this directly on your live site — a product
  card that displays a photo at 140×140 pixels is downloading a 1200×1200 pixel image, about
  73 times more picture data than the screen actually shows. Multiply that across the ~20
  product cards visible on the home page and it's a large, unnecessary amount of data for a
  customer on a limited mobile data plan.
  Status: Needs a future batch. Effort: Medium.
  Fix approach: generate a second, smaller image (e.g. 400px) at upload time specifically for
  grid/card use, and keep the current 1200px version only for the full-size product page
  photo viewer.

[MEDIUM — Code health] Two different places save the expert photo to two different files
  Admin → Settings → "Talk to an Expert" uploads to storage path
  settings/expert-photo.webp. The /contact page's own "Edit Mode" (ExpertEditSheet.tsx)
  uploads the same photo to a *different* file: expert-photo.webp (no folder). Whichever one
  you used most recently silently "wins" for what's displayed, and the old file from the
  other path is left behind in storage forever, unused. Business impact: confusing if you
  update the photo in one place and don't see the change, and slowly wastes storage space.
  Status: Needs a future batch (pick one path as the real one, delete the other). Effort: Small.

[LOW — Code health] Banner slides can be edited from two places that both save the same data
  BannerEditSheet.tsx (swipe-through edit sheet) and the "Banner Slides" panel inside
  SettingsTab.tsx both write to the same app_settings row. If two browser tabs/sessions have
  both open and save around the same time, one save can silently overwrite the other's
  changes. Not a security issue, just a "you might lose an edit" risk.
  Status: Needs a future batch (pick one as the real editor, or make the other read-only).
  Effort: Small–Medium.

[LOW — Security hardening, not urgent] Two database helper functions
  (is_admin(), is_wholesaler_or_admin(), admin_list_profiles()) don't pin down their own
  internal search path. This is a Postgres best-practice hardening step that Supabase's own
  security checklist recommends — in your specific setup the actual risk is very low (nothing
  exploitable was found), but it's a one-line-per-function fix that costs nothing to apply.
  See "SQL Naeem must run" below if you want it done.
  Status: Optional — SQL ready below. Effort: Small.

[LOW — Performance] All ~150 products load and render in one shot on the home page
  No pagination or "load more" — every visit fetches every active product in a single
  database call and renders every card into the page at once. With lazy-loaded images this
  isn't dramatic today, but it will get slower as the catalog grows past a few hundred items.
  Status: Report only for now, revisit once catalog grows. Effort: Medium.

[LOW — Code health] flag-icons library ships ~540 country flag SVGs (~4.8MB) for a site
  that in practice only ever shows a handful of countries (Bangladesh, Australia, reviewer
  countries). They're not downloaded until actually used on screen so this isn't costing
  load time today, but it's worth knowing this library exists in the project mostly unused.
  Status: Report only, low priority. Effort: Small if ever revisited.

5. NOTES FOR BATCH 16 (real orders) AND BATCH 17 (ads/analytics)
---------------------------------------------------------------------

Batch 16 — Orders table
  Good news: the checkout flow is already very well set up for this. useCheckoutState.ts
  already builds a complete "OrderSnapshot" object the instant "Pay and Order" is tapped —
  it already has every line item with its price *at the time it was added to cart* (so later
  price changes can't retroactively alter a placed order), the delivery zone, the full
  address, any promo code applied, and the computed subtotal/discount/total. This is
  essentially the exact shape an `orders` + `order_items` table needs — Batch 16 should be
  straightforward: take that existing OrderSnapshot and write it to two new tables instead
  of (or alongside) the current WhatsApp/PDF export.

Batch 17 — Pixel / Analytics / link previews
  Important limitation to know about: this is a client-rendered React app (a "SPA"), and
  Facebook's link-preview crawler does NOT run JavaScript. Your product pages already update
  their preview info (title, photo, price) live via JavaScript when a real browser opens
  them, but a bot fetching the raw page for a link preview only ever sees the one static
  description in index.html — never any specific product's actual name/photo/price.
  What this means in practice: if you share a specific product link on Facebook/WhatsApp
  today, the preview card will show your generic site image, not that product's photo.
  My recommendation for Batch 17: add a small Vercel serverless function that, only for
  requests coming from known link-preview bots (Facebook, WhatsApp, Twitter), serves a tiny
  pre-rendered HTML snippet with that specific product's real title/photo/price baked in —
  real visitors continue to get the exact same fast app they get today. This is the standard,
  well-understood fix for this exact problem on a Vercel-hosted SPA and doesn't require
  rewriting the site.
  Facebook Pixel and Google Analytics themselves are straightforward script-tag additions
  with no structural blockers I found.
