1. WHAT I DID
============================================================

WHY THE PAYOUT NUMBERS WERE WRONG (in two sentences)
  Steadfast lists every parcel in a payout with the COD it was BOOKED with,
  even a parcel it returned, and the site counted that booked amount as
  "collected" and then invented "other charges" to make the payout total
  still match. Separately, when Steadfast collected a different amount than
  the order's "COD via Steadfast" payment said, the site only flagged it
  and never corrected the order's paid amount.

WHY THE PROMO COUNTS WERE WRONG (in two sentences)
  Before Batch 18 (25 Sep) there were no real orders, and the success
  screen counted a use as soon as it opened. The counting function stayed
  open to anyone on the internet afterwards, so a code could be used up
  without any order. Also, cancelling or deleting an order never gave the
  use back.

Payouts — what I checked on the real data (34 payouts, 14 Jan – 16 Nov 2026)
  - Every payout's lines add up exactly to what Steadfast paid (34 of 34),
    before and after the fix.
  - No order is counted in two payouts.
  - All site-order lines are matched to exactly one order, except the ones
    listed below.

Payout logic errors found and fixed
  1. Returned parcel counted as cash collected.
     Payout SFC-27728657 (14 Jan 2026): parcel 127690312 was "cancelled"
     (returned) by Steadfast but recorded as ৳1,120 collected, and ৳1,120 of
     made-up "other charges" was spread over 16 other parcels.
       Before: COD collected ৳3,800, fees ৳2,473, paid ৳1,327
       After:  COD collected ৳2,680, fees ৳1,353, paid ৳1,327
     ৳2,680 is exactly what Steadfast says it collected. From now on, a
     parcel Steadfast returned always counts ৳0 collected and only its
     charge. That parcel was booked directly on Steadfast's website, so it
     was never in sales or profit; only the payout screen was wrong.
  2. The order's paid amount did not follow what Steadfast collected.
     NM-3327: the order said Steadfast collected ৳8,935; Steadfast actually
       collected ৳8,930 (the order total had been lowered to ৳8,930 after
       booking). The payment is now ৳8,930, and the order is still fully paid.
     NM-3329: the order said ৳1,199; Steadfast actually collected ৳1,150.
       The payment is now ৳1,150, so the order shows ৳49 STILL DUE. Either
       the rider gave the customer ৳49 off, or ৳49 is really owed. If you
       let it go, add a ৳49 discount on that order.
     From now on, whenever a payout shows a different COD than the order's
     "COD via Steadfast" payment, the payment is set to what Steadfast
     collected, the change is written in the order's history, and the line
     shows as Matched. If the month is locked, the payment is left alone
     and the line stays "to check" with the reason.
  3. A returned parcel's order was "to check" for no reason. If a parcel
     comes back and the order was marked returned, cancelled, or delivered
     by hand (trouble case 3), it now matches, as long as the order does not
     claim Steadfast collected cash. Steadfast's charge becomes that order's
     courier cost.
  4. A cancelled order's courier charge counted nowhere. Sales profit only
     looked at delivered and returned orders. A cancelled order that
     Steadfast still charged now shows in Sales profit with ৳0 sale and its
     charge as a cost (on the payout date). No real order has this today.
  5. Prepaid orders showed "Steadfast paid −৳61". An order paid in full in
     advance (trouble case 2) shows nothing collected and only the delivery
     charge kept, so its order page said "Steadfast paid −৳61". It now says
     "Steadfast collected nothing and kept ৳61 in fees on 16 Oct". The
     numbers were already right; only the wording was wrong. This was the
     "showing wrongly" case. No payout itself showed ৳0: all 34 payouts
     have their correct amount.
  6. A credit could break the sum (has not happened yet). If Steadfast ever
     pays MORE than COD minus fees (a credit), the old code dropped the
     difference, so the lines would no longer add up. The difference is now
     kept as a negative "other" amount, and the sum always matches.

The two parcels settled quietly

  NM-1721 (payout 16 Oct, SFC-32659519, ৳47.50 charge): found by its

  Both lines stay marked even when Steadfast is read again.

Promo codes
  - Applying, removing and re-applying a code in the cart only READS the
    code. It never changes times_used (that was already true in today's
    code; now there is a test for it).
  - times_used goes up by one only inside place_order, the same server step
    that creates the order. If the order fails, nothing is counted. Nobody
    else (not visitors, not signed-in customers) can call the counter now.
  - Cancelling or deleting an order that used a code gives the use back
    (never below zero). Reopening a cancelled order counts it again.
    A returned order still counts: it was a real order.
  - The cart still shows only "Invalid or expired code".
  - Orders DO store the code they used, so I recounted every code from real
    orders that are not cancelled. Today there is only one code,
    "11.11.OFFER1109": 1 use = 1 real order, so its count stays 1.
    Older orders used codes that have since been deleted (BLIS26, SORRY50,
    THANKYOU50, WELCOME200, WINTERASENAKNO); deleted codes have nothing left
    to recount.
  - Admin New order has no promo code field (it uses discount reasons), so
    there was nothing to change there.

5. DESIGN DECISIONS
============================================================
  - A payout line now has a "kind": order / courier_only / returned. It is
    one small column and the simplest way to mark NM-3315 and NM-1721
    without inventing orders.
  - Settled lines are protected by the database itself, not only by the
    website code. The protection works even before the Steadfast functions
    are redeployed.
  - The COD correction trusts Steadfast's payout over the booked amount,
    because the payout is the record of real cash. It only corrects an
    existing "COD via Steadfast" payment. It never creates one and never
    deletes one (that is why NM-3301 is left to you).
  - A courier-only line stays out of profit entirely (no sale, no loss).
    In the Money books it shows as "Courier only, not a shop sale", next to
    unmatched parcels, so the Steadfast balance stays true. If the friend's
    ৳75 went into an account you count, it may show up as a small count
    difference. It is before your money start date (13 Nov), so today it
    does not.
  - Returned orders keep their promo use; only cancelled or deleted orders
    give it back.
  - Testing: everything ran against the live database inside one
    transaction that was always undone. The payout screen test used
    made-up payouts answered in the browser. I checked afterwards that no
    test rows are left (no E2E-B46 product, code or payout), that the live
    schema is unchanged, and that Inventory mode is still On. I created no
    leftover rows, so nothing needed removing.

6. INDUSTRY-LEVEL SUGGESTIONS (not done)
============================================================
  1. Reconcile Steadfast every month (medium). A one-line monthly check —
     "Steadfast says it paid ৳X, you placed ৳X in accounts" — would catch
     a missing or double-placed payout before the month is locked.
  2. Single-use / per-customer promo codes (medium). Today a code has only
     a total limit. A code meant for one person can still be used by
     anyone who learns it. Tying a code to a phone number stops sharing.
  3. Alert on COD shortfalls (small). When Steadfast collects less than
     booked (like NM-3329), send a Telegram message straight away. Then you
     can call the customer while the delivery is fresh.
  4. A "parcel with no order" button (medium). Today, settling a parcel like
     NM-3315 needs SQL. A small choice on the payout line (courier only /
     returned) would let you do it yourself in future. Not built, because
     this batch was asked to add no new screens or workflows.
