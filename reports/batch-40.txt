5. DESIGN DECISIONS (choices I made for you, and why)
======================================================================
* "immutable": Supabase's upload can only set "max-age=<seconds>" (it writes "public, max-age=31536000"); it
  has no way to add "immutable". Because every upload now has a new name, a stored file never changes, so this
  has the same effect in practice.
* Existing photos are not re-compressed to 1400 px: they are already 1200 px or less, and re-encoding a WebP
  only loses sharpness. They become the "large" version as they are. New uploads are 1400 px.
* Card copies live in a "card" folder with the photo's own name (products/card/<id>.webp), so each photo's
  card is easy to find and unique, and the old "thumb" copies can be removed later in one go.
* The card copy is 480 px, quality 0.82: a typical card photo is ~20 KB (smaller than the 40–80 KB the brief
  allowed — better for egress, and still sharp at 2.6× phone screens).
* Videos: cut to the first 20 seconds (a banner loops anyway), no sound, 720p. Some video encoders refuse to
  go below a certain size at 720p, so the tool tries 720p, then 720p at 24 frames a second, then 540p, until
  it is under 1.5 MB. The video tool (Mediabunny library, ~590 KB) loads only when an admin makes a video small
  — customers never download it, and the offline helper doesn't pre-download it either.
* A video that can't be made small is NOT stored; the brand shows a still picture from it (the brief: "keep
  the poster image only").
* Shop-down page: WhatsApp is the one orange button (the main action), Messenger outlined (CLAUDE.md: one
  orange element per screen). It also covers slow connections: if the first data takes over 8 seconds the
  page shows, and it switches to the shop by itself the moment the data arrives.
* Tests: placeholders instead of real photos also make the test screenshots show grey squares instead of
  product photos — the layout is the same.

   wasted data on a customer's phone plan.
