BATCH 16 — Customer Google Login + Account Page + Smart Address
====================================================================

SUMMARY
-------
Built: Google-only customer login, a real account page, and a Division→
District→Thana address picker (with Dhaka/Chattogram city areas added — the
public dataset was missing them). Login is only asked for at checkout, never
while browsing. Security first, as instructed: a test customer account could
not gain admin/wholesaler powers, see wholesale prices, or write to anything
it shouldn't — every existing protection already keyed off the real role, not
just "is logged in." One real bug found while building this: a cold page
load straight onto checkout (exactly what happens right after the Google
redirect) was bouncing the customer to an apparently-empty cart — fixed.
Build and tests both pass.

PART 1 — SECURITY: WHAT I CHECKED, WHAT I CHANGED
-----------------------------------------------------
Read every RLS policy, view, RPC, and storage policy in supabase/*.sql for
anything treating "is authenticated" as "is admin/wholesaler" — that exact
bug existed once (migration-004, already fixed), and Google login reopens the
same risk since now any Google account becomes "authenticated."

Result: every write policy (products, categories, app_settings, reviews,
bento_tiles, product_variants, promo_codes, both storage buckets) already
gates on is_admin() or is_wholesaler_or_admin() — real functions that check
the profiles table, not just "logged in." Google login adds no new risk there.

What DID need a change: profiles.role only allowed 'wholesaler'/'admin', and
nobody could update their own row at all. migration-020 adds a 'customer'
role with three layers so a bug in any one can't cause self-escalation:
  1. Self-insert only accepts role='customer'+status='approved', or the
     existing role='wholesaler'+status='pending' — never admin.
  2. A new self-update policy: a signed-in user may only touch their own row.
  3. A trigger (prevent_profile_self_escalation) hard-blocks any UPDATE that
     changes role/status/approved_at unless the caller is already admin —
     plain OLD/NEW comparison, no ambiguity. This is the one piece worth a
     second read if you want to sanity-check it yourself before running it.
Also scoped admin_list_profiles() (the Wholesalers tab's data source) to
role='wholesaler' only, and bundled in Batch 15's optional search_path
hardening for is_admin()/is_wholesaler_or_admin() since this migration
already touches them.

Couldn't test against a real customer session (Google isn't configured yet),
but re-verified live, as a real anonymous request, that wholesale_price still
returns null everywhere and every admin table is still write-protected —
unchanged from Batch 15. The migration file's own "Verify" section has five
copy-paste checks to run as a real logged-in customer once Google is on.

BUG FOUND & FIXED — cold-load redirect race
------------------------------------------------
DeliveryDetailsPage/OrderSummaryPage decide "cart is empty" by resolving the
cart against the loaded product catalog, which starts empty and loads over
the network. Fine when clicking through from the cart page (catalog's
already loaded), but the Google redirect lands fresh on /checkout/delivery —
catalog still empty — and the page redirected straight back to /cart before
the catalog had a chance to load, even though the cart was fine. Fixed by
having both pages wait for the catalog before deciding the cart is empty.
Confirmed via a real cold load onto /checkout/delivery, before and after.

DISTRICT/THANA → DELIVERY ZONE MAPPING (please confirm)
------------------------------------------------------------
Only two zones exist today (Inside Dhaka ৳80, Outside Dhaka ৳130) — mapping
lives in one file, src/lib/deliveryZones.ts:
  - District=Dhaka, Thana=one of the 50 DMP areas (Mirpur, Dhanmondi,
    Gulshan, Uttara East/West, Mohammadpur, Badda, etc.) → Inside Dhaka
  - District=Dhaka, Thana=Savar/Dhamrai/Keraniganj/Nawabganj/Dohar (Dhaka's
    outer upazilas) → Outside Dhaka — my judgment call, see below
  - Every other district (incl. Chattogram city) → Outside Dhaka

Judgment call: Steadfast prices Savar/Keraniganj/Dhamrai cheaper than
"outside Dhaka" but pricier than central Dhaka — a third tier the app
doesn't have. Mapped those five to Outside Dhaka since ৳130 is closer to
Steadfast's real cost than ৳80 would recover. A real third zone with its own
fee is a small follow-up if you'd rather have one.

Steadfast's order API (for a later batch's real courier booking): couldn't
reach their docs live — looks like it sits behind a merchant login. Worth
confirming directly once you have API credentials; third-party write-ups I'm
aware of describe a plain free-text address field, but treat that as
unconfirmed until you see their real docs.

DATASET USED + WHAT WAS ADDED
----------------------------------
Base: nuhil/bangladesh-geocode on GitHub (713 stars, the standard public
dataset) — 8 divisions, 64 districts, 494 upazilas, English+Bangla, bundled
into src/data/bangladeshGeo.ts at build time (no runtime API calls).

As warned in the brief, its "Dhaka district" only lists 5 rural upazilas.
Added on top, from Bangla Wikipedia's DMP/CMP articles (cross-checked against
the English versions):
  - 50 Dhaka Metropolitan Police areas
  - 15 Chattogram Metropolitan Police areas (CMP has 16; "Karnaphuli" thana
    was left out — Chattogram already had a near-identical "Karnafuli" rural
    upazila, and showing both would confuse the picker)
Total: 559 Division/District/Thana entries.
