PART 1 — Automatic daily backup (free)
  - Where: a PRIVATE GitHub repo, naeemBro17/naeems-backups.
      db/2026-10-07.dump.gpg   one file per night (the whole database:
                               orders, payments, customers, products,
                               brands, settings, staff, logins)
      storage/files/...        copy of every image, logo and video
      storage/files.tsv        list of every Storage file (path, size, date)
      last-check.txt           the last restore test, table by table
  - When: every night at 03:00 Bangladesh time (21:00 UTC), plus a
    "Run workflow" button (GitHub → naeems → Actions → Nightly backup).
  - Kept: the newest 30 nights + the first backup of each of the last 12
    months; older ones are deleted automatically. The repo keeps only ONE
    commit (each night replaces it), so deleted backups really disappear
    and the repo never grows past what is kept (~3 MB per night today).
  - Safe: each file is encrypted (gpg, AES-256) with BACKUP_PASSWORD. The
    job refuses to save if the backups repo ever becomes public. Your
    main repo is public, so its Action logs are public too: the job prints
    only pass/fail lines and table names — never data or row counts (those
    are in last-check.txt inside the private repo).
  - Every night it proves the backup: decrypts it again (same bytes),
    checks the main tables are in it (orders, order_items, order_payments,
    products, product_variants, profiles, brands, categories, staff,
    logins, storage list), restores it into a throw-away Postgres 17
    INSIDE the job (never the live database) and compares every table's
    row count with the backup. Any difference = the job fails.
  - Storage: CHOSEN = full copy every Sunday. Today: 375 files, 31 MB
    (product-images 238 files / 13.9 MB, brand-media 137 files / 17.5 MB).
    Unchanged files are not downloaded again. If it ever passes 300 MB it
    switches to saving only the list (files.tsv).
  - Alerts: backup failed → Telegram "Backup failed on <date> — check
    GitHub Actions" (same bot and chat as order alerts). Sundays: one
    quiet line "Backups OK — last 7 days saved." Success otherwise = no
    message. GitHub also e-mails you when a scheduled run fails.
  - How the alert reaches Telegram: a small new Supabase function
    "backup-alert". It can send only those two fixed messages and needs its
    own secret (BACKUP_ALERT_SECRET), so even a leaked secret can't send
    anything else.
  - Access to the backups repo: a "deploy key" (an SSH key that can write
    to naeems-backups and NOTHING else), stored as the secret
    BACKUP_DEPLOY_KEY. Chosen over a personal token because it is limited
    to one repo, never expires, and I can set it up without you clicking.
  - Cost: nothing. GitHub Actions is free (unlimited minutes for a public
    repo, ~5 min per night), a private repo is free, Supabase free plan.
  - docs/RESTORE.md: step by step, in plain English: download, unlock,
    restore into a NEW test Supabase project (with the warning never to
    restore over the live shop without help), images and videos.
  - Restore test result: see section 10 (first real run).
  Proof: actionlint (workflow) + shellcheck (script) clean; unit tests
  for the keep-30-plus-12-monthly rule; e2e "Part 1" checks the workflow.

PART 2 — Fraud check before confirming (staff only)
  - New steadfast function action "fraud_check" (GET
    /fraud_check/score/{phone}). Only staff with "View orders"; customers
    and visitors are refused before Steadfast is asked.
  - IMPORTANT, Steadfast changed this: the old answer with exact counts
    (delivered / returned) stopped on 27 Sept 2026. The new answer gives:
    the parcel count as merchants see it ("7", "10+", "25+", "50+",
    "100+"), the delivered % and the returned %, and how many times other
    merchants reported the number. So the card shows:
        Parcels 50+ · Delivered 92% · Returned 7%
    (exact totals are no longer available from Steadfast).
  - Colours: delivered ≥ 80 % green, 50–79 % amber, < 50 % red with
    "High return risk — consider an advance payment". No history → "No
    courier history yet" (grey, not red — Steadfast says a number with no
    history must not be shown as clean OR as bad).
  - Shown in the order detail (right under Call / WhatsApp / Invoice) and
    in New order as soon as a full mobile number is typed or picked.
  - Cached 24 h per number (one Steadfast call per number per day) in a
    new staff-only table steadfast_fraud_cache; "Refresh" asks again (never
    within a minute). Phone typed any way (+880 / 880 / 0 / spaces).
  - If the action fails or isn't deployed: nothing is shown, no error.
  Proof: 3 e2e tests (all colours, caching, refused, missing action),
  unit tests on Steadfast's own example answer; screenshots admin-order-
  {good,warn,risk}-*, admin-new-order-fraud-*.

PART 8 — Small images
  - WHY some cards still loaded full photos: 91 of your 98 products had
    the FULL photo's address saved as their "small copy". When making a
    small copy failed, the old code saved the full photo in its place, so
    the product looked done — the button stopped counting it, and editing
    the product re-used it. The copies failed because the shop's offline
    helper keeps product photos in an unreadable ("opaque") form once they
    have been seen in the shop, and the generator was handed that copy
    instead of the real photo. Only photos added since 26 Sept (7
    products) had real small copies.
  - Fixed: the generator downloads the photo fresh; only a real small copy
    counts as done; a failed one is retried next time.
  - "Generate small images" now covers products, variant photos and the
    Browse circles (160 px copy), skips what is done, shows "N of M done"
    and a done message. Where: Admin → Products, next to "Add" (a button
    on PC; in the ⋮ menu on a phone), plus the existing notice on that
    page while anything is missing.
  - New / changed photos get their small copy automatically on save
    (products as before; now also variants and categories).
  - Cards and circles use the small copy when it exists, otherwise the
    full photo — never a broken image.
  - YOUR ONE STEP: open Admin → Products → ⋮ → Generate small images once
    (keep the page open ~2–3 minutes). Home will then load far fewer MB.
  Proof: unit tests; e2e checks the cards and runs the tool with Storage
  and saves mocked (nothing written) on a product without a small copy.

    expiry, no clicking). One-commit backups repo (deleted backups really

    see before pressing Confirm.

    need them); Team still shows e2e.admin (security: never hide a Super
    Admin login from you).
  - Page titles changed from "Naeem's" to "NAEEM'S" everywhere so the name
    is one spelling (the header wordmark design is untouched).
  - App updates: "prompt" mode (we choose the moment) instead of the old
    automatic mode that never switched the running app over.
