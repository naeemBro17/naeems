Part 1 — Checked Batch 20 against Steadfast's real docs

Read the PDF you saved to Downloads ("API guide — Merchant Dashboard —
Steadfast Courier Limited.pdf" — an export of their actual dashboard page,
your real API keys visible in its sample code, which is exactly why I
didn't copy it into the repo or quote those keys anywhere). Compared it
line by line against Batch 20's code. Batch 20 had been built from a
third-party GitHub library instead — right on the basics, wrong or
incomplete on a few real things:

  RIGHT already (no change needed):
    - Base URL: https://portal.packzy.com/api/v1
    - Headers: Api-Key, Secret-Key, Content-Type
    - create_order's field names, and that invoice/recipient_name/
      recipient_phone/recipient_address/cod_amount are the required ones
    - status_by_cid's response shape ({status, delivery_status})
    - Only "delivered" and "partial_delivered" count as truly delivered —
      the docs explicitly warn every "_approval_pending" status is "the
      rider's word, not ours yet", and Batch 20 already only trusted the
      confirmed two.

  WRONG or MISSING (fixed):
    - Real per-parcel tracking link. Batch 20 assumed no such thing existed
      and pointed customers at the generic steadfast.com.bd/tracking page
      (where they'd have to type in a code themselves). The real
      create_order response includes "tracking_link":
      "https://steadfast.com.bd/tl/xxxxxxxx" — a direct link straight to
      that one parcel. Now saved (steadfast_tracking_link) and used for
      both the customer's "Track parcel" link and a new one in the admin
      order screen. Old/never-booked orders just keep falling back to the
      generic page, since nothing was ever actually booked yet.
    - The full status list. The docs list 12 delivery_status values, not 7
      — Batch 20's list was missing exceptional (lost/damaged) and all four
      "_approval_pending" variants. It didn't cause a wrong DECISION (the
      "counts as delivered" check was already narrow enough to be right by
      luck), but the code's own comments claimed a shorter list than
      reality — now corrected to the real 12, in one shared file so both
      Edge Functions read the same list.
    - Error messages on a rejected booking. The docs show a rejected
      create_order comes back as {"status": 400, "errors": {"field":
      ["message"]}} — a per-field breakdown, not a plain "message" string.
      Batch 20's code only ever read `message`, so a bad phone number or
      address would have shown you a bare "Steadfast rejected the request
      (HTTP 400)" instead of which field and why. Now reads `errors` first
      and shows the real field-by-field reason.
    - COD amount limit. The docs state a hard 1,000,000 BDT cap (rejected,
      not just truncated). Added a check before ever calling Steadfast, so
      an oversized order shows a clear message instead of a raw rejection.
    - Rate limits, confirmed: 1,000 requests/minute generally, 6,000 for
      booking specifically, and status answers are cached 60 seconds on
      Steadfast's side (so polling faster than that "tells you nothing
      new" — their own words). This is what the 3-hour automatic refresh
      interval below is sized against.

No direct tracking-LINK-you-can-hand-a-customer-without-them-typing-
anything existed as a separate documented feature beyond the one inside
create_order's own response — so nothing extra to add there beyond saving
that field, which is now done.


Part 2 — Automatic status updates

The PDF confirms Steadfast DOES support webhooks ("Give us a webhook URL
and we'll tell you when a parcel moves") and even shows a "Webhooks" button
in the dashboard's own navigation — but the PDF you exported only captured
the "API guide" page, not that separate "Webhooks" page, so the actual
payload shape and how to verify a callback really came from Steadfast
were not in the file I could read. Rather than guess that shape (exactly
the mistake this whole batch exists to fix), I used the other option the
brief allowed: a scheduled job.

What's built:
  - A pg_cron job, every 3 hours, calls a new Edge Function
    (steadfast-refresh-all) that checks every order that's shipped AND has
    a real Steadfast consignment id — same status_by_cid call the manual
    "refresh" button already makes, just for every shipped order instead of
    one at a time.
  - Since there's no admin logged in for a background job, that function
    proves it's really your own cron job (not a stranger hitting the URL)
    with a long secret token, checked before it does anything — the same
    "long secret token" approach the task described for a webhook, applied
    here to my own cron call instead since the webhook's real shape wasn't
    available to me.
  - Delivered/partially delivered → marks the order delivered, with a
    history row, exactly like the manual button already does.
  - Cancelled / on hold / exceptional (lost or damaged) → the order's own
    status is NEVER touched automatically, exactly as instructed. Instead,
    it now sends you a Telegram message the moment that first happens — I
    found your existing order-notification system (Batch 18, the one that
    already messages you for new orders and cancellations) is wired to
    fire on every single update to any order, so I extended that same
    function rather than building a second notification path. Nothing new
    for you to configure in Telegram or the Supabase dashboard for this
    part — it reuses your existing bot token/chat id.
  - The admin Orders list and an order's own detail screen now show a
    "Needs attention" badge whenever its Steadfast status is one of those
    three, so it's visible even without Telegram.
  - The manual "book" and "refresh" buttons, and the "Update all shipped"
    bulk button, are all untouched and still work exactly as before —
    nothing about Part 2 removes or changes them.

DESIGN DECISIONS
-----------------
- Chose a fresh, purpose-built secret (STEADFAST_CRON_REFRESH_SECRET) for
  the cron job to prove itself, rather than reusing Supabase's own master
  service-role key in that role — if this one token were ever exposed, the
  worst it can do is trigger a status refresh; it can't read or change
  anything else in your database.
- Kept the automatic-refresh write path (system_update_steadfast_status)
  completely separate from the admin-button path
  (admin_update_steadfast_status) instead of merging them — the automatic
  one has no admin session to check, so weakening the existing admin
  check to allow that would have meant every future admin-only Steadfast
  action inherits the same weaker check. Two small functions, one obvious
  trust boundary each, felt safer than one function with a "trust me,
  this caller is fine" exception folded in.
- Reused the existing Telegram notifier instead of building a second
  alert path — it already fires on every order update, so extending its
  own "is this worth telling Naeem about" logic was less code and one
  fewer thing to keep in sync than a new function with its own secrets.
