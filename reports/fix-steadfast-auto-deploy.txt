A BUG I FOUND AND FIXED DURING DEPLOY
--------------------------------------
steadfast-refresh-all is called by our own pg_cron job, which sends our
custom secret as the Authorization header — not a real Supabase login
token. Supabase Edge Functions check the Authorization header themselves
by default (checking it's a real signed token) BEFORE your own function
code ever runs. Our custom secret isn't that kind of token, so every
single cron call would have been silently rejected by Supabase itself,
with the function's own secret-check code never even reached. The 3-hourly
automatic refresh would have looked "deployed" and "active" but would
never actually have updated a single order.

Fixed by redeploying that one function with Supabase's own JWT check
switched off for it (`--no-verify-jwt`) — the function's own secret check
(already written, already correct) is what actually protects it; this only
removes a redundant platform-level check that was actively wrong for a
cron-triggered function. Confirmed the fix by calling the function
directly with no secret at all: it now returns the function's own
{"ok":false,"error":"Not authorized."} (HTTP 401) instead of Supabase's
generic gateway rejection — proof the request is reaching our code.

Also added supabase/config.toml (didn't exist before) with just this one
setting recorded, so a future redeploy of this function doesn't silently
turn the platform check back on and reintroduce the same silent failure.
This file is new; it does not touch or override anything for the other
two functions, which keep their normal JWT check untouched.
