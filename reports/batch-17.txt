BATCH 17 — Category Chips, Search Rebuild, Animation Audit
====================================================================

SUMMARY
-------
Found the real cause of the chip-scrolling bug — a CSS trap, not a timing
issue like Batch 10 assumed — and fixed it with a pinned duplicate bar,
verified live at every category tested. Rebuilt search into its own screen
(recent searches, live suggestions, results with a count, all surviving
Back-navigation via the URL) matching Daraz/Shopee-style search. Audited
every open/close interaction on the site; found and fixed three real "opens
but doesn't close" bugs. Build and tests both pass.


PART 1 — CATEGORY CHIPS
----------------------------
Root cause (confirmed live, not assumed): the chip row's wrapper
(.home-section, one per reorderable homepage section) is exactly as tall as
the chip row itself — a live test showed both at exactly 59px. CSS
`position: sticky` can only stick within the height its own parent box
gives it room to move through; with zero spare height, sticky did nothing
useful no matter how it was tuned. This is why Batch 10's timing fix didn't
help — the bug was never about when the scroll ran, it was that scrolling
the chip row into view always ends with it under the fixed header once the
page is tall enough, because there was never really anything holding it in
place after that.

Fix: a second, always-mounted copy of the chip row, fixed just below the
header, that fades/slides in exactly when the original has scrolled up past
the header and fades back out when scrolled back above it (plain scroll
listener, rAF-throttled). Tapping either copy filters the same way and
re-highlights both. Tapping a chip now scrolls to a manually computed
position (chip row's real offset minus header height) rather than relying on
scrollIntoView, which was the piece silently depending on sticky actually
working.

Verified live (dev build, real product data):
  - Body Care (13 products): tapped from top of page → pinned bar's
    getBoundingClientRect().top measured 60, header's own bottom edge also
    60 — flush, no gap, no overlap. Confirmed both directions: scrolling
    down past the original row shows the pinned copy (opacity 0→1,
    top:60px), scrolling back up hides it again (opacity back to 0).
  - Selecting a category from the Browse circles (not the chip row) lights
    up the matching chip in both copies and scrolls the same way.
  - Active-chip horizontal scroll-into-view (e.g. Hair Care sitting off the
    right edge of the row) confirmed via the new per-chip ref map in
    CategoryChips.tsx.
  - Eye Care (1 product) and All (104 products) both filter and highlight
    correctly; with so little content on Eye Care the page may not be tall
    enough to ever trigger the pinned bar at all, same as before — that's
    correct, not a bug, there's nothing to scroll past.
Not independently re-measured at exactly 360px/390px device width — this
dev environment's viewport didn't respond to resize commands, but the
layout itself has no breakpoint between 360-640px (confirmed in app.css),
so the 480px-capped content column measured above renders identically
across that whole range.

src/styles/app.css


PART 2 — SEARCH
--------------------
New dedicated screen at /search (src/pages/SearchPage.tsx), reusing the
existing Fuse.js matching (src/hooks/useSearch.ts — unchanged, already
case-insensitive and already matches brand + category name, so left alone
per the brief) rather than rebuilding search itself:

  1. Tapping the home search bar (now a button, not a live input —
     SearchEntryBar.tsx) or the bottom nav's Search tab goes straight to
     /search. No hero, Browse circles, bento grid, or chips there.
  2. Empty: recent searches (persistent list, not the old focus-only
     dropdown) with per-term remove + Clear all, plus up to 8 category quick
     picks.
  3. Typing 2+ characters: a live suggestions dropdown (thumbnail + name)
     floats over the results grid, which is already updating live
     underneath it — confirmed live: typing "cerave" showed "16 products"
     and a real CeraVe-only grid the instant the dropdown appeared.
  4. Results: count line ("16 products found") + the same ProductGrid/
     ProductCard as the home page, including its existing empty-state
     ("No results for '...'", suggests clearing the search).
  5. Query lives in the URL (?q=cerave), synced one-directionally
     (query→URL, replacing not pushing, so typing doesn't spam browser
     history) so a reload or shared link restores it.
  6. Confirmed live: searched "cerave", opened a product from the results,
     pressed Back → landed back on /search?q=cerave, input showed "cerave"
     again, the same CeraVe grid was showing at very close to the same
     scroll position, and — checked directly —
     document.activeElement was <body>, not the input, so no keyboard
     popped up. That was the specific bug named in the brief; it's fixed by
     never auto-focusing on a return trip (only ever on a genuinely fresh,
     empty entry into the page).
  7. Clear (×) on the input; Back arrow returns to home.

One design call: the brief's example result-count text was given in both
Bangla and English ("১৩টি প্রোডাক্ট পাওয়া গেছে" / "13 products") — used the
English form since every other piece of site chrome (buttons, labels,
empty states) is English throughout; only the Batch 16 checkout login
moment was asked to be Bangla specifically.
