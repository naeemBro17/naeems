DECISIONS MADE WITHOUT ASKING
-----------------------------
1. Context file lives at src/contexts/AdminEditContext.tsx, not src/context/.
   The project already has src/contexts/ (Auth, Product, Theme); a second
   folder differing by one letter would be a trap.

2. AdminEditProvider wraps the whole router (App.tsx), not just ViewerPage.
   Otherwise Edit Mode switches itself off every time you move between the
   homepage and /contact, because each route remounts. It still resets on
   reload and sign-out as specified.

3. Product edit sheet: "Description / note" became two fields, Note and
   Description. They are separate columns with separate jobs (note = short
   line under the price, description = "About this product"). Merging them
   would have destroyed data.

4. Product edit sheet regenerates the URL slug when the name changes, same as
   the admin form does. A renamed product gets a matching URL; old shared
   links still resolve through the SKU fallback.

5. Reorder lists have up/down arrow buttons in addition to the drag handle.
   HTML5 drag-and-drop does not fire on touch screens, and this UI is used
   on a phone. Both work; the arrows are the reliable one on mobile.

6. Bottom Carousel sheet: Section A (expert card) is saved by the Save button;
   Section B (custom tiles) saves each change immediately — toggle, delete,
   reorder, and the add/edit form each write straight to bento_tiles. The
   spec said "updates app_settings and bento_tiles as needed", and mixing
   both into one Save would have meant a partial-failure mess.

7. Expert card "subtitle" is a new app_settings key, bento_expert_subtitle.
   The card previously hard-coded "Skincare Expert". Empty = that default.

8. Expert photo: uploads to the new 'expert-photos' bucket at a fixed path
   (expert-photo.webp, overwritten each time, cache-busted by query string).
   The upload happens on file selection with a progress overlay; the URL is
   written to app_settings on Save. Admin → Settings still uses the older
   path in product-images. Both write the same key, so either works.

9. Wholesale price in the product sheet is editable, but the value shown when
   the sheet opens comes from products_view — which only returns it to an
   admin. That is by design (the same security boundary as everywhere else).

10. Left/right-top bento tiles: the sheet lists what the tile currently shows
    (default allocation, or your saved order). A product you un-feature later
    drops out of the saved order automatically rather than leaving a hole.

11. Edit pencils fade out (not just disappear) when Edit Mode turns off. To do
    that they stay mounted for an admin. For anyone who is not an admin they
    are not rendered at all — verified by checking the anonymous DOM.

DECISIONS MADE WITHOUT ASKING
-----------------------------
1. What "swap" means with a tall tile. The left tile always spans both rows,
   so it owns a whole column. Swapping it with a short tile moves it to the
   other column and stacks the two short tiles in the column it left. The
   saved order ["right_top","left","right_bottom"] therefore renders as:
   right_top top-left, right_bottom bottom-left, left (tall) on the right.
   Placement is computed from the order (src/lib/layoutOrder.ts), never
   hard-coded, per the "use grid-row span" instruction.

2. Swiping inside the bento tiles is paused while Edit Mode is on. A press
   on a tile may become a 500ms long-press drag, and letting the same touch
   also drive the stack/carousel swipe produced accidental slide changes.
   Turn Edit Mode off to preview the swipes.

3. Mouse drag works too. The brief said touch, "not mouse events only"; the
   hook wires mousedown/mousemove/mouseup to the same flow so the feature is
   usable at a desk. Touch remains the primary, tested path.

4. Pessimistic save without a flicker. On release the dragged item snaps to
   its destination and stays there while the save runs; the real reorder
   applies when the refetched settings arrive, and the held transform is
   cleared in the same paint. If the save fails the item slides back and a
   red toast appears. Nothing is reordered in local state before the
   server confirms.

5. Section handles overlay content, so while Edit Mode is on the "Browse"
   title, the chip row and the banner text step right by ~44px to make room.
   Customers never see this shift.

6. While a section is being dragged the page cannot scroll (the touch is
   captured). All four movable sections fit on one screen, so no
   auto-scroll was built.

DECISIONS MADE WITHOUT ASKING
-----------------------------
1. Fuse keys are exactly name / brand / category name, as specified. The old
   search also matched SKU and the short note; those are no longer searched.
   SKUs are hidden from customers anyway.

2. A one-character query shows the full default grid, not an empty one. The
   brief asks for the dropdown "after 1 character" but also sets Fuse's
   minMatchCharLength to 2, so a single character can never match anything.
   Rather than flash "no results" between the first and second keystroke,
   sub-2-character queries behave like an empty query; the dropdown appears
   from the second character.

3. Fuse runs with ignoreLocation: true (not in the brief). Without it a match
   has to sit near the start of the name, so "refill" would miss
   "CeraVe Foaming Cleanser Eco-Recharge Refill 473mL".

4. Tapping a recent term fills the bar, runs the search and closes the
   keyboard (blurs the input) so the results are visible. The dropdown does
   not re-open for that term until the user types again.

5. The X clear button empties the bar; with the bar still focused and empty
   the Recent panel then shows, per the Part 3 rules. The autocomplete
   dropdown disappears because there is no longer a query.

6. Both panels overlay the page (absolute, z-index 100). The brief only
   required this of the autocomplete; the Recent panel does the same so the
   hero banner never jumps when the bar gains focus.

7. The skin-tag chips sit at the very bottom of the inline product sheet,
   after Images, per "at the bottom of the product edit form". They are not
   in Admin → Products (the full-page form) — that form leaves the columns
   untouched on save, so nothing is lost.

8. The 150ms search debounce was removed. Fuse over ~100 products is well
   under a millisecond, and the suggestions need to feel instant.

DECISIONS MADE WITHOUT ASKING
-----------------------------
1. Variant wholesale prices use exactly the products pattern rather than a
   separate SECURITY DEFINER function: product_variants_view computes
   wholesale_price with the existing is_wholesaler_or_admin() helper (which
   IS the SECURITY DEFINER function) and returns NULL to everyone else, and
   the base table's column is locked to all API roles. One query serves
   customers, wholesalers and admins; the brief's "fetch wholesale_price
   separately" step isn't needed. There is no database role for "admin" in
   Supabase — admins are authenticated users with a profile row — so
   "admin gets SELECT on the base table including wholesale_price" cannot
   be expressed as a grant; admins read it through the view like
   wholesalers do, and the editor pre-fills from that.

2. Variants are loaded once for the whole catalog (one query on the view,
   alongside products) so the card can show "from ৳X" without a request per
   card. The detail page reads the same data; a product that had to be
   fetched directly (not in the loaded list) fetches its own variants.

3. A product's variant editor saves each variant immediately, as specified,
   then reloads the shared variant list — so the card's "from" price and the
   detail page follow at once without a full product refetch.

4. The card's Copy Price copies the "from" price when the product has
   variants, matching what the card shows. The detail page copies the
   selected variant's price.

5. The variant's in_stock flag drives the detail page's stock row and Copy
   Price when a variant is selected; the product-level stock_quantity is
   ignored there. The card still shows product-level stock.

6. Region is stored uppercased ("us" → "US") so chips read consistently.

7. The variant sub-form is a div, not a <form>: it sits inside the product
   sheet's form and nested forms are invalid HTML. Enter in any of its
   fields saves the variant, not the product.

Session 9 (Product Card Cart-Button/Badge Overlap), 2026-09-16
================================================================
No new migrations.

SIGNIFICANT DEVIATION FROM THE BRIEF
-------------------------------------
The brief described a bug where the cart button is
`position: absolute; bottom: 12px; right: 12px` and overlaps the "Save X%"
badge, and asked for a CSS Grid/Flexbox two-zone rewrite reserving a 42px
right column for the button. That bug did not exist in this codebase:
- There is no "cart" anywhere in the app (grepped the whole src/ tree).
- The card's action element is `.copy-button` ("Copy Price" / "Copied!"),
  full-width, sitting in its OWN row below the stock row via
  `flex-direction: column` + `margin-top: auto` on `.copy-button`
  (src/styles/app.css:3281). It is not absolutely positioned and cannot
  overlap the price/save badge above it — they're stacked in normal flow,
  not side by side.

Rewriting the button into a small 42px grid-column icon slot as literally
specified would have deleted the "Copy Price"/"Copied!" text states (no
room for the label) and removed a working, previously-verified feature for
no functional gain, since there was no overlap to fix.

What I actually did: the one real, applicable defect was Part 3's concern —
`.product-card__price-sub` (retail strike price + save badge) had no
`flex-wrap`, and the card's outer `overflow: hidden` (for rounded corners)
meant a long strike price + a high discount badge (e.g. "Save 45%") could
in theory get clipped at the ~160-180px 2-column mobile card width. Fixed
by adding `flex-wrap: wrap` (+ `white-space: nowrap` on each child so they
don't break mid-token, + `flex-shrink: 0` on the save pill) to
`.product-card__price-sub` in src/styles/app.css. Retail price now wraps to
its own line with the save badge below it if the row genuinely runs out of
room, instead of clipping.

Verified at real ~160-180px 2-column card width using a static harness
(reused the actual compiled CSS + markup, not the live app — the dev
server requires Supabase credentials I don't have) with all four specified
data cases (short name/brand, long name/brand, high discount "Save 45%",
no discount at all) plus adversarial extreme values (very long strike
price + "Save 99.99%") to confirm the wrap fallback actually engages when
needed. In every case the button never overlapped text (structurally
impossible, separate flow row) and the badge never clipped.

`npm run build` passes with zero errors.
