PART 1 — Promo code usage limit (the money bug)
I checked the whole path end to end before changing anything, as instructed.
The validation logic, the database function that increments times_used, and

  - Applying a code checks active + max_uses/times_used + expiry (lib/promoCodes.ts).
  - migration-014-promo-codes.sql already defines increment_promo_usage() as a

  - OrderSuccessPage already calls it exactly once (a ref guards against

So the code was not the bug. The far more likely explanation, per the
project's own known failure pattern, is that migration-014 (or the specific
function inside it) was never actually run against the live database — a
missing RPC function fails silently, which looks exactly like "the limit
isn't enforced." I hardened the one weak spot I found: the call to
increment_promo_usage was pure fire-and-forget with no error visibility at
all, so a missing function would fail completely silently forever. It now

ACTION NEEDED FROM YOU: see the SQL section below — please re-run

PART 2 — Back button from product edit goes to Home
Root cause found: every sheet/modal in the app (the product edit form, the
inline product editor, confirm dialogs, the hamburger menu, etc.) is pure
on-screen state — it never told the browser "something opened." So pressing
the phone's back button had nothing to close; it skipped straight past the
sheet to whatever page was open before you ever opened /admin (often Home).
Fixed with one small shared hook (src/hooks/useModalBackClose.ts) wired into
the two components every sheet/modal in the app is built from
(components/shared/Modal.tsx and BottomSheet.tsx). Opening a sheet now
registers one invisible "back stop" with the browser; back closes the sheet
instead of leaving the page, and closing any other way (Cancel, tapping
outside, Escape) cleans that stop up automatically so you never need an extra
back-press afterwards. Because this lives in the two shared building blocks,
it fixes the bug everywhere at once — not just the product editor — without
touching each sheet individually.
Filter/search/scroll state was already preserved (the admin list never
actually unmounts when a sheet opens), so nothing else was needed there.
The product detail page uses real page navigation (not a sheet) and already
had correct back + scroll-restore behaviour — verified, left alone.

PART 3 — No way back to Home from checkout
Cart, Delivery Details and Order Summary already had a back arrow in the
header (BackButton, already wired correctly, and cart contents are never
cleared just by navigating away). The one real gap was the final success
screen — it had no way out at all besides two action buttons. Added a
"Continue Shopping" button back to the product grid, right below the
WhatsApp/PDF actions, per the spec.

PART 4 — Expert card blocks page scrolling
Found the exact bug: the shared swipe hook (hooks/useSwipe.ts), used by the
bottom-right carousel tile (the expert card + any custom tiles) and the
featured-products stack tile, called preventDefault() on every touchmove the
instant a finger touched it — before it even knew whether the gesture was
horizontal or vertical. That's the exact anti-pattern flagged in CLAUDE.md.
Rewrote it to be direction-aware: it now waits until movement is clearly
along its own axis (more than ~10px and clearly more than the other axis)
before capturing the gesture at all. A finger that lands on the expert card
and moves vertically now scrolls the page normally; only a genuine
horizontal swipe is captured. Also changed the carousel tile's CSS from
touch-action: none to touch-action: pan-y, so the browser handles vertical
panning natively as a second line of defence, per CLAUDE.md's rule.
Checked every other horizontally-swipeable element on the site: the product
image carousel and the hero banner both use plain native horizontal scroll
(no JS touch capture at all), and the category rows (Browse circles, chips)
do too — none of them had this bug.

PART 1 — Instant product open (the 2-second delay)

Found the real cause, and it was not what the task guessed. The theory was
that the detail page waits on a Supabase fetch before it can paint. I checked:
when you tap a card from the grid, that exact product is already sitting in
the app's in-memory catalog (the same list that rendered the card), so the
detail page was already resolving it instantly with no network call — that
part was never actually the bottleneck.

The real cause: last session's hero transition (the card image morphing into
the detail page image) tagged EVERY product card in the grid — all ~100+ of
them — with the marker the browser uses to know what to animate, not just the
one being tapped. Every single tap, the browser had to prepare an individual
animation snapshot for all ~100+ real product photos before it could show
anything, even though only one of them was actually going to move. That is a
well-known, expensive mistake with this browser feature, and it would be far
worse on a phone's GPU than in a desktop browser — matching exactly the "taps
and stares at the old screen" symptom.

Fixed it at the source: only the card actually tapped gets tagged now, set at
the instant of the tap rather than in advance on every card. Confirmed by
directly counting tagged elements before and after a tap: 105 before this fix,
1 after. Confirmed by clicking a real card in the running app: the URL and the
new page both update within the same tick, no visible delay.

On top of that fix, I also built what the task asked for directly, as
genuine extra insurance (and because a couple of its individual requirements
were real, even though the "waiting on a fetch" theory wasn't the main
story):
  - The exact product row a tapped card was already showing is now handed to
    the detail page through the navigation itself (router state), so the
    very first render has real data to paint from no matter what — it
    doesn't have to depend on the catalog context noticing in time.
  - The transition is never awaited on anything — it starts in the same
    click handler that changes the page, before any network activity.
  - Opening the same product again is already instant and always was — nothing
    is re-fetched, since the catalog is loaded once and kept in memory for the
    whole visit.
  - Direct/shared-link opens (no card to inherit data from) still go through
    the original fetch-then-render path — but that full-page spinner has been
    replaced with a shaped skeleton (an image-sized block, name-sized bars, a
    price-sized bar) that matches the real layout, so it doesn't jump around
    once the real content arrives.

One thing genuinely does not apply to this app and I did not force it in: the
task asks for "the top paints instantly, the bottom fills in afterward with
its own skeleton." This app fetches a product's entire row in one query —
image, name, price AND description, how-to-use, ingredients, video, variants
— there is no second, slower fetch for the lower half of the page to begin
with. Building a fake split-loading state for data that already arrives
together would have added real complexity for no actual benefit, so I didn't.

Also found and fixed a real bug while looking at the rendered detail page for
the first time: the "Copy Price" button was still rendering orange (it was
supposed to become the neutral secondary action once "Add to Cart" became
the primary one, from last session's checkout-colour work). The CSS rule that
made it neutral existed, but was declared BEFORE the button's base style in
the stylesheet, so the base orange was winning. Moved it after. Confirmed on
screen: Add to Cart is now the only orange element on the page, Copy Price is
neutral grey, and the green "Copied!" flash still works on both states.

PART 2 — Product card layout

Verified on a REAL narrow viewport this time (see section 3 below for exactly
how, since the standard browser tools here can't shrink below ~650px). Tested
at 320px, 360px, 375px and 390px — the full realistic phone range, not just
the 160-180px the task asked for.

What I actually found, measured directly against every rendered card rather
than guessed:
  - The price-wrapping bug (Problem B) and the badge/cart-button collision
    (Problem C) did NOT reproduce at 375-390px (a modern phone) with the code
    as merged from last session — but they reproduced on EVERY single card
    once the viewport dropped to 320px (an older/smaller phone), which is
    still a real device width. So the bug was real, just narrower than where
    it was originally seen — plausibly the live phone tested against had a
    slightly narrower effective width, or different font metrics, than my
    360-390px checks alone would have caught.
  - Fixed it at the root instead of chasing the exact width: shortened the
    save badge from "Save 12%" to "-12%" (same idea the task offered as the
    fallback) on every card, consistently, and added `white-space: nowrap`
    to the price, the struck-through retail price and the badge so none of
    them can ever break internally again, at any width. Also shrank the cart
    button a little further (30px, then 28px) exactly as the task allowed,
    to free more room.
  - Re-measured after the fix at all four widths: zero cards wrap at any of
    them, and the gap between the badge and the cart button is never below
    7px even at the extreme 320px width (it's 35-42px at realistic
    375-390px widths). No collisions found anywhere in the ~105-product
    catalogue.
  - Problem A (names truncating early) is real but only partly fixable with
    CSS alone. I confirmed exactly why: with a long name like "CeraVe Foaming
    Cleanser Eco-Recharge Refill 473mL" at card width, the word "Recharge"
    (8 letters) simply doesn't fit in what's left of the second line after
    "Cleanser Eco-", so it wraps whole to a third line that then gets cut —
    leaving a visible gap on line 2 before the ellipsis. I tried both
    automatic hyphenation (`hyphens: auto`) and character-level breaking
    (`word-break`) directly in the running browser to see if either would
    tighten that gap — neither changed the outcome, because browsers only
    break inside a word when the word cannot fit ANYWHERE on its own, never
    just to pack a line more tightly. That is a hard limit of how text
    wrapping works, not a bug in this app, and the task explicitly ruled out
    the other usual fix (shrinking the font). What I could do — and did — is
    free up real width by shrinking the cart button further, which reduces
    how often this happens without touching font size. A handful of the
    longest names in the catalogue will still show a modest gap on their
    second line; renaming those specific products to something shorter is
    the only way to fully close that gap, and that's a content decision, not
    a code one.
  - Checked every required case by hand at 375px: longest name (Aveeno Baby
    Daily Moisture Fragrance Free Lotion), long name with a hyphenated word
    (CeraVe Foaming Cleanser Eco-Recharge), medium name (Beauty of Joseon Red
    Bean Water Gel), short out-of-stock name (Bio Oil | 200mL — confirmed its
    save badge correctly disappears because it's out of stock, and the cart
    button shows disabled), and the largest discount badges in the catalogue
    (all "-XX%" now, same width regardless of the digits). Also confirmed a
    genuinely no-discount product shows just its price with no leftover gap.

Confirmed the bug exactly as described, at 375-390px: "Aveeno Daily" filled
maybe two-thirds of line 1 and then jumped "Moisturising" whole to line 2,
leaving real empty space behind. Measured it precisely before touching
anything: the word "Moisturising" (12 letters) simply didn't fit in what was
left of line 1, so the browser moved the entire word down rather than
splitting it — normal, correct CSS text-wrapping behaviour, just not the
behaviour this card needs.

The task suggested `overflow-wrap: anywhere` as the fix. I tried it, then
checked with an isolated test in the real browser engine whether it actually
changed anything — it did not. I want to be precise about why, since it
matters for any future styling decision like this: `overflow-wrap` (in
either its `break-word` or `anywhere` form) only ever breaks a word that
doesn't fit ANYWHERE — i.e. is wider than the whole line box on its own. It
does not break a word that merely doesn't fit in what's left of a
partially-filled line but WOULD fit comfortably starting fresh on the next
line — and "Moisturising" easily fits on its own line at this card width, so
neither property touched it. I verified this with a direct side-by-side
comparison of "normal" wrapping vs. "anywhere" on the exact failing text at
the exact failing width — the line breaks were byte-for-byte identical.

The property that actually does what's needed is `word-break: break-all`,
which allows a break at any character boundary regardless of whether the
word would fit on a fresh line. Applied it, then looked at the real result
on every name the task asked me to check:
  - "Aveeno Daily Mois / turising Lightly S…" — both lines now fully used.
  - "Aveeno Oat Milk B / lend Moisturisin…" — both lines fully used, but the
    break lands after a single letter ("B"), which does look like a stray
    character rather than an intentional break.
  - "Beauty of Joseon / Relief Sun Aqua-F…" — breaks fall at natural word
    boundaries here regardless, so this one looks completely normal.
  - "CeraVe Foaming / Cleanser Eco-Rec…" — fills further than before
    (previously broke after "Eco-", now after "Eco-Rec"), reads fine.
  - "Bio Oil | 200mL" — short name, unaffected, still reserves the full
    two-line height so price rows stay aligned with longer-named neighbours.
I also tried combining this with automatic hyphenation (`hyphens: auto`) to
see if the browser would insert a proper hyphen at a real syllable break
instead of an arbitrary character split — it made no difference; break-all's
break opportunities override hyphenation's the same way they override normal
word boundaries.

name, which is what was required. The genuinely honest trade-off, per the
task's own instruction to report rather than silently revert: a small number

PART 4 — Variant delete was closing the whole sheet

Reproduced it exactly as described: opened a product with 3 variants,
deleted the middle one, and the entire "Edit Product" sheet closed and
dropped back to the grid.

Root cause, and it's a real bug in shared code (src/hooks/useModalBackClose.ts),
not anything specific to variants: every sheet/modal in this app pushes one
"fake" browser-history entry while open, so the hardware/browser back button
closes it instead of leaving the page. When it closes normally (Cancel,

opens a small confirm dialog (nested inside the product sheet); confirming
the delete closes that dialog, whose cleanup's history.back() was
accidentally closing the whole product sheet above it.

real back-press" right before it pops its own entry, so a parent sheet
still open at the time can tell the difference. This is a shared hook, so
the fix protects every nested confirm-dialog-inside-a-sheet in the app, not
just variants.

5. DESIGN DECISIONS
--------------------------------------------------------------------
- Part 1's line-splitting is done in JavaScript (measuring real text width
  with a canvas), not CSS. I want to be upfront that this is a bigger
  hammer than a CSS tweak — the reason is in Part 1 above: CSS genuinely
  cannot express "prefer whole words, but break one specific word if
  skipping it whole would waste the rest of the line," which is exactly
  what a two-line card with truncation needs. I checked this claim by
  testing the actual behavioural difference in the real browser before
  writing any code, not just reasoning about it.
- Part 4C's ?variant= URL parameter uses the variant's real database id (a
  UUID) rather than a human-readable slug like the task's own example
  (?variant=usa-473ml). A slug needs its own generation/uniqueness rules
  (what happens with two variants that would produce the same slug, special
  characters in a region name, etc.) and the id already does the actual
  job asked — a link that reopens to the right variant — with zero new
  edge cases. Happy to build a prettier slug later if you would like the
  URL to read nicer when shared.
- Part 5's variant selector on the detail page changed from a two-tier
  Region-then-Size grid to a single flat row of chips (each chip shows its
  full "Region - Size" label). This was a necessary side-effect of adding
  Part 7's combine flow: a combined product's options don't necessarily
  share a clean region-by-size grid the old two-tier picker assumed (e.g.
  one option might have no region at all, or the options might be
  genuinely unrelated sizes from different original products) — a flat
  list handles every case correctly, including the common, clean case,
  without the old layout's assumption. Existing products with real
  region/size variants will look slightly different (one row of chips
  instead of two) but work the same way.
- Part 7's combine flow deliberately does NOT touch the manual "add a
  variant by hand" editor at all — they're two separate, independent ways
  to end up with variants on the same product, exactly as the task asked,
  and I verified both still work side by side on the same product.
